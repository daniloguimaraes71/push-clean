# 05 · UI / UX Specification

The human architect has delegated UX decisions to this document. It is prescriptive:
the agent **implements exactly this** and does not invent extra screens, flows, or
flourishes. Where a detail is unspecified, prefer the simplest thing that satisfies
the tests and matches the spirit below.

Design intent: calm, low-friction, "glanceable." This is a gentle daily nudge, not a
productivity command center. Avoid notification-fatigue patterns and visual clutter.

---

## Navigation map

```
RootNavigator
├── (no home yet)  → OnboardingStack
│                      └── OnboardingScreen
└── (home exists) → MainTabs
                     ├── Today      (Dashboard)      [default tab]
                     ├── Settings   (SettingsScreen)
                     └── Home Info  (HomeSummaryScreen, read-only)
```

Routing rule: on launch, fetch the user's homes. None → Onboarding. One or more →
MainTabs with **Today** selected. Keep it to these three tabs; no drawer, no nested
stacks beyond onboarding.

---

## Screen 1 — Onboarding (the guided home description)

Purpose: collect a structured **text** description of the home. The schedule is always
generated by the text-only scheduling model; an optional image scan (when the backend
enables it) is just a faster way to fill in that text.

Layout, top to bottom:
0. **(Optional) "Scan a blueprint or photo"** button (`testID="scan-blueprint-btn"`).
   Rendered **only when** `GET /capabilities` returns `vision_onboarding: true`. On
   press: pick an image (`expo-image-picker`) → `POST /homes/describe-from-image` →
   pre-fill the notes field (and, where parseable, room rows) with the returned text
   for the user to review and edit. This never bypasses the review step; the user
   always confirms before generating. When the capability is false, this button does
   not exist and onboarding is form-only.
1. Title: "Tell us about your home."
2. Home name field (`testID="home-name-input"`, default "My Home").
3. **Room builder** — a dynamic list. Each row (`testID="room-row-{index}"`):
   - "Room name" text input (placeholder `Room name`).
   - "Floor type" — a select/segmented control (Tile / Hardwood / Carpet / Other);
     for test simplicity it also accepts a text input with placeholder `Floor type`.
   - Remove button (`testID="remove-room-{index}"`).
   - "Add room" button below the list (`testID="add-room-btn"`).
4. Household size stepper (default 2).
5. "Any pets?" toggle.
6. Notes free-text (`testID="notes-input"`, placeholder "Anything else? e.g. prefer
   light daily upkeep").
7. **Generate Schedule** button (`testID="generate-btn"`).

Behaviour:
- `generate-btn` is **disabled** until ≥1 room has a non-empty name (test
  `FE-ONBOARD-VALIDATION-01`).
- On press: assemble `description_text` by concatenating rooms and notes into a
  readable sentence (must contain each room name and floor type — test
  `FE-ONBOARD-SUBMIT-PAYLOAD-01`), then `POST /homes/onboard`.
- While loading: show a spinner and disable the form.
- On error: show an inline banner (`testID="error-banner"`) with a retry; never crash
  (test `FE-API-ERROR-SURFACE-01`).
- On success: navigate to MainTabs → Today.

## Screen 2 — Today (Dashboard, the checklist)

Purpose: the daily checklist. This is the screen users see most.

Top: **date ribbon** — a horizontal, swipeable row of date chips centered on today,
showing roughly the past week through today (do not allow far-future dates in the
prototype). Chips: `testID="date-chip-yesterday"`, `date-chip-today`, etc. Selecting
a chip refetches (`getDaily(date)` — test `FE-CHECKLIST-DATE-NAV-01`). This is the
**pagination model**: date-based, not numbered pages, not infinite scroll.

Body: tasks grouped under room headers. Each task row:
- Checkbox (`testID="task-checkbox-{completion_id}"`), label (task name), and a
  small meta line ("~5 min" and an "overdue Nd" badge when `overdue_days > 0`).
- Tap anywhere on the row toggles completion: optimistic flip, then
  `completeTask({completion_id, completed})`; on failure, revert and show a toast.
- Completed tasks show a strikethrough and move to the bottom of their room group.

Empty state: friendly message ("All clear for today 🎉" or, for a brand-new home
with nothing due, "Nothing scheduled for this day.").

Interactions:
- **Pull-to-refresh** re-fetches the selected date.
- First load also triggers push-permission + token registration (see Screen 3 note
  and test `FE-PUSH-TOKEN-CAPTURE-01`).

## Screen 3 — Settings

Purpose: control notifications and scheduling intensity. Loads via `getSettings`,
saves via `putSettings` (debounced; each committed change persists — test
`FE-SETTINGS-SCREEN-01`).

Controls:
- "Morning briefing" toggle + time picker (`morning_time`).
- "Evening nudge" toggle + time picker (`evening_time`). Helper text: "Only sent if
  you have unfinished tasks."
- "Daily task limit" stepper (`daily_intensity_cap`, 1–12) with
  `testID="intensity-decrement"` / `intensity-increment`. Helper: "How many tasks we
  suggest per day."
- Read-only "Notifications enabled" indicator reflecting OS permission + whether a
  push token is registered.

Push token: on first Dashboard mount, request permission; if granted, fetch the Expo
token and `registerPushToken`. Persist the token in the Zustand store and mirror to
the backend. If permission is denied, show a non-blocking note in Settings.

---

## Screen 4 — Home Info (read-only)

Shows the parsed plan: rooms, floor types, and each room's chores with frequency
("every N days") and estimated minutes. Includes the LLM `confidence_score` as a
small "AI confidence" chip. A single "Re-generate plan" button may be present but,
for the prototype, it simply re-runs onboarding for a new home (no in-place edit).
No editing of individual chores in the prototype.

---

## State management (Zustand)

Three stores, persisted to `AsyncStorage` where noted:

- `useUserStore` — `userId`, `timezone`. (persisted)
- `useSettingsStore` — the settings object + `expoPushToken`. (persisted) Hydrates
  from backend on launch; writes through to backend on change.
- `useScheduleStore` — `selectedDate`, `tasksByDate` cache, loading/error flags.
  (not persisted; always fresh from backend)

Optimistic updates live in `useScheduleStore`: toggling updates local state first,
then reconciles with the server response, reverting on error.

---

## Visual style (lightweight guidance)

- A single accent color, generous white space, large tap targets (≥44pt).
- System font; one size scale (title / body / caption).
- No animations beyond default navigation transitions and the checkbox toggle.
- Respect light/dark via React Native's `useColorScheme`.

Keep it boring and reliable. The product value is the schedule and the nudge, not
the chrome.
